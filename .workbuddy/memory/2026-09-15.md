## https 回环回调 → 改为「粘贴授权码」通道

用户给出的平台回调是 `https://localhost:10009`（OAuth 2.1 loopback 常见做法本是 http，但平台登记什么就得照抄什么）。桌面端只有明文 HTTP 监听、无 TLS 证书，https 跳转必然打不开页面，但 **code 仍在地址栏里**，故新增手动通道：

- `WorkBuddyAuthController.makeAuthorizationURL(clientID:scope:redirectURLOverride:)` 抽出链接构造并记住 state，供 UI 单独使用
- `WorkBuddyAuthController.canServeRedirect(_:)` 判定能否自动接收（仅 http + localhost/127.0.0.1）
- `WorkBuddyAuthController.completeWithPastedCode(...)` 接受完整回调 URL 或裸 code；带 state 就校验，只粘 code 则 `skipStateCheck`
- `exchange` 增加 `skipStateCheck` 参数；新增 `WorkBuddyAuthError.missingAuthorizationCode`
- 设置页：授权行增加「粘贴授权码」按钮；`connectWorkBuddy` 判定不可自动接收时只开浏览器 + 提示，不起本地服务；`pasteWorkBuddyCode` 弹 NSAlert + NSTextField 收集链接

不采用自签证书方案：浏览器会拦不受信证书，还需塞进系统信任链，代价大于收益。

联调脚本：`/tmp/wb_token.py <code或完整URL>` —— 换 token → 写钥匙串（service `app.agentstick.mac.workbuddy`，account `client_secret`/`oauth_token`）→ GET /localassistant 验证在线。注意 Swift `JSONEncoder` 对 Date 用 secondsSince2001，python 侧换算要减 978307200。

## 平台回调地址改动需重新审核（关键约束）

用户在开放平台把回调从 `https://localhost:10009` 改成 `http://localhost:8799/oauth/callback` 后，`/authorize` 仍报 400 `redirect_uri is not registered`，而用旧的 10009 反而能正常跳转（页面"连接失败"是跳转成功、本地无服务的表现）。

结论：**改动回调地址后要重新提交审核，审核通过前新值不生效、旧值仍有效**。联调期间不要把旧值当失效。

本次先用 10009 + 粘贴授权码拿 token；审核通过后再把 `config.toml` 的 `[agents.workbuddy] redirect_uri` 改成 http 值并重新授权一次，即可全自动。

## 回调服务必须双栈监听（已修）

`WorkBuddyOAuthCallbackServer` 原来只 `bind(AF_INET, 127.0.0.1)`。macOS `/etc/hosts` 里 `localhost` 同时解析到 `::1`，浏览器可能先试 IPv6，导致跳转丢失（表现为"地址栏已是 localhost:8799 但服务器没收到请求"）。

改为 IPv4 `127.0.0.1` + IPv6 `::1` 各起一个监听（IPv6 保持 V6ONLY 默认，不开局域网），queue 改 `.concurrent` 让两个 `accept` 并发阻塞；`listenSocket: Int32` → `listenSockets: [Int32]`，`acceptLoop(on:)` 带 fd 参数，stop() 遍历关闭。已编译通过。

排查时另注意：本 Bash 环境有 `HTTP_PROXY=http://127.0.0.1:58947`，`curl localhost:8799` 会走代理返回 502，不能用来判断本地连通性（系统代理 ExceptionsList 里 localhost 是例外的，浏览器不受影响）。

## 授权已跑通，端到端验证通过

**授权码有效期很短（人工复制地址栏的 2–3 分钟就会失效，报 `invalid_grant: code not found, expired or already used`）**，必须自动即时换取。

可行做法（`/tmp/wb_oauth_https.py`）：本机 10009 起**自签证书 TLS 服务**（openssl 生成 SAN=localhost/127.0.0.1，`ssl.SSLContext` wrap HTTPServer，IPv4+IPv6 双栈），收到跳转立刻在同一进程内换 token。浏览器（Zen/Gecko 系）弹证书警告，点「高级 → 接受风险并继续」即可。

结果：
- token 到手，scope = `user.localassistant.invokable user.localassistant.readable`，expires_in 86400
- `GET /localassistant` → `{"online": true}`
- 钥匙串已写入并加 `-T <app路径>` 预授权，避免 app 读取时弹窗

**端到端实测（`/tmp/wb_send.py`）**：`POST /localassistant/message {"content":..,"msg_type":"text"}` → 返回 `message_id` → `GET /localassistant/message?message_id=..` 轮询 → assistant 回复。真实返回结构已确认：

```json
{"messages":[{"message_id":"..","role":"assistant","msg_type":"","content":[{"text":"收到","type":"text"}]}]}
```

要点：响应体是 `{code,msg,data}` 信封，取 `data`；`msg_type` 在 assistant 回复里是空串（不影响 permission/question 判定）；`content` 是数组、元素为 `{"text":..,"type":..}`——`replyText` 的 `[String:Any]["text"]` 分支正好覆盖，无需改。

用户浏览器是 **Zen**（Gecko 系）。

## 设置窗口被撑宽、无法调窄（已修）

现象：加了 WorkBuddy 区块后设置窗口变得很宽、拖不动。原因不是窗口本身，是 `hintRow()` 用 `NSTextField(labelWithString:)` 且**不换行**——单行固有宽度 ≈ 文字全宽（那条中文提示约 1700px），撑大 stack 的 fittingSize → 经 clip view 传导迫使窗口变宽。

修法（`SettingsWindowController.swift`）：
- `hintRow` 提示文字改为 `.byWordWrapping` + `maximumNumberOfLines = 0` + `preferredMaxLayoutWidth` + 水平 compression resistance `.defaultLow` + `widthAnchor <= hintMaxWidth`（`<=`，不再是 `>=300`）
- 新增 `private enum SettingsWindowLayout`（rowLeading 132 / outerMargin 24 / windowWidth 640 / minWindowWidth 560 / hintMaxWidth 计算值），窗口 minSize 宽度 640 → 560
- 那条超长中文提示拆成两条

教训：这个项目里所有 `hintRow` 文本都会参与 stack 的固有宽度计算，以后加长提示必须换行限宽，否则窗口会被内容顶宽。

无硬件的注入式验证入口不存在：`agent-events.sock`（`AgentStickCore/AgentEventBridge.swift`）是 AgentStickHooks → App 的事件回传服务，不是任务下发口；App 无 os_log/NSLog/文件日志，也没有 CLI 参数或 URL scheme。因此真机 E2E 只能靠用户对着设备说话，再检查 `~/Library/Application Support/AgentStick/Tasks/`。

## 「粘贴授权码」失败 + 连接按钮变灰（已修，v0.3.13 已重装）

用户粘贴 `https://localhost:10009/?code=...&state=...` 后报「授权回调失败，请重新连接」，且「连接 WorkBuddy」按钮一直灰色。

诊断手段（有效，以后照做）：把用户给的 code 直接用 curl 打 `/token`，服务端返回 `{"error":"invalid_grant","error_description":"code not found, expired or already used"}` → 先分清是**码过期**还是**客户端校验拦截**。同时 `security find-generic-password -s app.agentstick.mac.workbuddy -a oauth_token -w` 读出令牌后 `GET /localassistant` 得到 `online: true` → 说明钥匙串里早就有有效令牌（iat 为 53 分钟前），本次粘贴其实是多余的重授权，不影响已授权状态。

三个真实缺陷：
1. `completeWithPastedCode` 里带 state 就做校验，而 `pendingState` 在 App 重启/新 controller/超过 10 分钟 `pendingExpiry` 后就没了 → 直接 `.stateMismatch`（即用户看到的那句话）。手动粘贴是带外传输，state 校验没有安全收益，改为 `skipStateCheck: true`，交给服务端判码。
2. `connectWorkBuddy` 在 https 分支（不可自动接收）设了 `isEnabled = false` 却从不恢复 → 按钮永久灰色。现已恢复，并把授权链接同时写进剪贴板（浏览器唤起失败时可手动粘贴）。
3. 码过期报的是服务端英文串；新增 `WorkBuddyAuthError.codeExpired`，`tokenRequest` 遇到 invalid_grant/expired/already used/not found 时映射成「授权码已失效（有效期约 2 分钟）。请重新点"连接 WorkBuddy"，授权后立刻粘贴。」

另：粘贴弹窗会预填剪贴板里含 `code=` 的 URL（同时排除带 `response_type` 的授权链接），缩短复制-粘贴往返；提示文案加了 2 分钟有效期。

安装复查：`strings`/`grep -a` 在本环境查二进制里的中文会漏（都返回 0），用 Python 读 bytes `.count(s.encode())` 才准——已确认新包含「授权码已失效」。钥匙串两条目已用 `security add-generic-password -T <新包路径>` 重建预授权。

构建注意：`AGENTSTICK_TARGET_ARCHS="arm64"` 必加，否则脚本默认编 x86_64 并在 AgentStickHooks 链接阶段失败（`__swift_FORCE_LOAD_$_swiftCompatibility56`，CommandLineTools 的兼容库只有 arm64 切片）；打包阶段 `rm -rf build/AgentStick-*.app` 与 `.sparkle-staging` 会触发 SAFE_DELETE（>50 文件），需先 `mv` 到 /tmp。`swift build` 仍需要 `/tmp/swift-shim`（`exec /usr/bin/swift "$@" --disable-sandbox`）并 `PATH=/tmp/swift-shim:$PATH`，否则编 manifest 的 sandbox-exec 被拦。**重启 App 不能用 `osascript quit`**（无 AppleScript 支持，静默失败，进程仍在跑旧二进制），用 `pkill -x AgentStickApp`。

链路（`VoiceStickCoordinator`）：`runAgentCLI` 完成回调（主线程）→ `playAgentSoundIfEnabled("task_done", to: peripheralID)` → `BleCentral.playSound` → BLE `{"event":"play_sound","sound":"task_done"}` → 固件 `main.c:578` 映射到 `AUDIO_PLAYBACK_SOUND_TASK_DONE`。另有 `sendAgentCompletionNotification`（UNNotification，`content.sound = .default`）。开关 `agent_sound_alerts_enabled`（默认 true，实测配置里为 true），音量 `device_sound_volume = 46`。

已排除：
- 固件名字对得上（`task_done` 有 3 段 tone）；`apply_app_ui_state("notification")` 不会中断播放
- 任务确实成功结束：`Tasks/20260915-154020-workbuddy.md` exit 0（注意 **文件名时间戳是写文件时刻，不是任务开始时刻**，用 `stat -f %SB` 看的是创建时间，两者同源）
- WorkBuddy 派发分支与 claude 共用同一个完成回调，我的改动（`AgentCLIRunner`/`AppConfig`）没碰声音链路

本环境 `log show` 完全读不到（任何 predicate 都 0 行），拿不到 NSLog，所以静态无法确认是「指令没发」还是「发了没响」。

采取的改动（v0.3.13 重装）：
1. **新增 `AgentDebugLog.swift`**：可选落盘日志，仅当 `~/Library/Application Support/AgentStick/agent-debug.log` 存在时才写（>512KB 停写）。已记 run start / run finished / play_sound 目标与 skips。
2. `BleCentral.playSound` 改 `@discardableResult -> Bool`，写入方式 `.withoutResponse` → **`.withResponse`**（丢了提示音是真故障，丢了字幕不是）；目标设备不在时回退广播到任一已连设备。
3. `playAgentSoundIfEnabled`：设备都没送达时，用 `NSSound(named:)` 播本机兜底声（task_done=Glass / needs_input=Ping / 其他=Basso）。
4. 审批与提问回调里 `ble`/UI 调用收敛到 `DispatchQueue.main.async`——WorkBuddy runner 是从后台队列调 handler 的，而 `CBCentralManager` 的队列是 main。
